# Spec 模板（to-spec 中文化）

> 规范是拍板之后、拆票之前的产物：把会话里的想法与决策合成一份可拆票的实施方案。
> 模板从本仓四份既有方案（content-quality / q7 / mattpocock-skills / product-deep-dive）的共性提炼。
> 用法：复制本模板到 `docs/<feature>-plan.md`，逐节填写；无内容的节写「无」并说明，不删节。

```markdown
# <特性名> 方案

> 状态：草稿 / 待拍板（决策点见 §N）/ 已拍板
> 日期：YYYY-MM-DD · 作者：<agent/人>
> 姊妹篇：<相关既有方案引用，无则删本行>

## 0. 结论摘要
（三到五句：是什么、为何值得做、引入什么、不引入什么、预期收益）

## 1. 问题陈述与取证
（现状的代码级证据：文件/行为/数据，不是感受。每个抱怨给根因定位）

## 2. 背景与研究
（一手来源引用；本仓先例；外部方案对照。引用落 docs/ 或给 URL）

## 3. 方案设计
（分层/分线/分批结构；与现状逐项对照表：概念 × 既有实践 × 差距 × 动作）

## 4. 分批落地
（批次表：每批范围、文件清单、预估量；批间依赖）

## N. 决策点（待拍板项）
| # | 决策 | 选项 A（推荐） | 选项 B | 推荐理由 |
（推荐答案必须领先，用户可以一词接受）

## N+1. 验收与度量
| 批次 | 度量 | 目标值 | 采集方式 |
（可判定判据；量化目标）

## N+2. 风险与权衡
（编号列表：每项风险 + 控制策略）

## 范围外
（显式不做的事，防止范围蔓延）
```

## 写作纪律（writing-for-agents 要点落地）

- **正向指令**：写「每段以可验证事实收尾」而非「不要写空洞总结」
- **完成判据**：每步以可判定条件收尾，不写「确保质量」类空载
- **指针优先**：细节推到引用文件，正文留主干（上下文成本）
- **单一事实源**：一个定义只在一处权威出现，他处指针
- 拍板后：状态行改「已拍板」，决策表补「拍板结果」列（日期 + 依据）
